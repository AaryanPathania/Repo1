1. INTRODUCTION

Timely and well‑controlled material requisition is critical for operational efficiency. Legacy paper/email‑based processes suffer from missing information, rework, long cycle times, and poor auditability. This project implements a Requisition Management System that digitizes the end‑to‑end flow—from capturing requests, routing for approval, issuing from store, to final posting—using Business Central (BC) customization in AL. The solution follows standard ERP patterns (Header/Lines, number series, dimensions) and integrates inventory posting via Item Journal Lines while allowing granular validations and role‑based access.

Key Outcomes:

  • Single source of truth for requisition data.
  • Enforced approvals with line‑level control of approved quantities.
  • Store issuance and posting with dimension propagation.
  • Visual cues for urgency and short‑closed documents.
  • Audit trail and historical views of completed requisitions.

2. LITERATURE REVIEW

  • Manual requisition pitfalls: fragmented communication, missing approvals, data duplication, limited traceability.
  • ERP approach: Centralized data model (Header/Lines), controlled workflows, audit logs, and dimension‑driven analytics.
  • Business Central & AL: Provide extensibility for tables, pages, actions, triggers, and codeunits to tailor procurement/issuance flows. This project leverages BC’s standard entities (Location, Item, Item Journal Lines, Inventory Setup) and augments them with custom objects for requisition orchestration.

3. AIM & SCOPE

3.1 Aim

Design and implement a complete, extensible Requisition Management module using BC AL that covers creation, approval, issuance, posting, and audit, with robust validations and role‑based UI.

3.2 Scope

  • Creation: Structured header (Table 50098) and lines (Table 50099).
  • Approval: HOD approves at line level (approved quantity), or rejects with remarks.
  • Issuance: Store issues quantities up to approved amounts; supports lot/serial tracking.
  • Security: Page‑level access via User Setup flags.
  • Audit: Status, user IDs, timestamps, and remarks retained.
  • Analytics: Dimensions (current and “New” target dimensions) for financial reporting.

4.2 Data Model

4.2.1 Table 50098 – Requisition Header (Parent)

Purpose: Stores document‑level context—who, what, where, when, and workflow state. Primary Key: No. (Code[20]).

Core Fields & Behavior

  • No. (Code[20]) – document identifier. Number Series lookup via AssistEdit.
  • Date (Date) – set on insert to Today.
  • Location (Code[20]) – relation to Location; OnValidate → Updatelines() to sync child lines.
  • Global Dimension 1/2, GD 3 – current dimensions; on validate → Updatelines().
  • New Global Dimension 1/2, New GD 3 – target dimensions for the movement.
  • Requisition Type (Option: Transfer) – future‑proof.
  • Status (Option: Open, Approval For HOD, Approved) – drives UI access and actions.
  • Priority (Option: "", Urgent, As Per Schedule) – used for styling.
  • Required By Date (Date) – validation: Required By Date ≥ Date.
  • Audit fields – User Id, Requested by, HOD Approval ID, ISSUED By.
  • Completely Posted (Boolean, readonly) – set true when all lines are fully issued.
  • Short CLosed (Boolean, readonly) & Short CLose Remarks – early closure via ShortClosed().

Key Procedures & Triggers

  • OnInsert(): sets Date := Today; populates requester fields.
  • AssistEdit(OldRH): choose Number Series; assign next No.
  • Updatelines(): push header fields to every line.
  • ShortClosed(): requires remarks; removes pending Item Journal Lines; marks Short CLosed := true.

4.2.2 Table 50099 – Requisition Line (Child)

Purpose: Itemized request details; linked to Header via Document No. + Line No. (clustered key).

Core Fields & Behavior

  • Document No. (Code[20]) – FK to Header.No.
  • Line No. (Integer) – unique per document; auto‑incremented.
  • Item No. (Code[20]) – relation to Item; OnValidate fills Description and UoM.
  • Description (Text[100]) – default from Item.
  • Unit of Measure (Text[50]) – default from Item’s Base UoM.
  • Location (Code[20]) – copied from header by Updatelines().
  • Required Quantity (Decimal) – user request quantity.
  • HOD Approved Quantity (Decimal) – approver sets; OnValidate sets Remaining Required Quantity.
  • Quantity to Issue (Decimal) – store sets; must not exceed Remaining Required Quantity.
  • Issued Qty. (Decimal) – cumulative issued across postings.
  • Remaining Required Quantity (Decimal) – auto‑managed (Approved – Issued).
  • Required By Date (Date) – copied from header; store planning.
  • Stock In Hand (FlowField) – SUM Warehouse Entry.Quantity for Location, Item No., bin = 'MAINSTORE'.
  • Dimensions – mirror header via Updatelines().

4.3.2 Page 50231 – Requisition Card (Card)

Primary entry/edit page for headers.

trigger OnAfterGetRecord()
begin
    varEditable := true;
    case Rec.Status of
        Rec.Status::"Approval For HOD":
            varEditable := false;
        Rec.Status::Approved:
            varEditable := false; // Only store has special editable fields on subform
        Rec.Status::Open:
            varEditable := true;
    end;
end;

Only one role edits at a time per workflow stage, preventing tampering or accidental overwrites.

4.3.3 Page 50232 – Requisition Subform (ListPart)

  • Bound to Requisition Line (Table 50099); SubPageLink = Document No.=field(No.).
  • AutoSplitKey = true; inherits parent varEditable.
  • Open: requester edits; Approval For HOD: locked; Approved: store sets Quantity to Issue.

4.3.4 Pages 50233/50234/50235 – Approval Pages

  • List shows Status = "Approval For HOD".
  • Approver enters HOD Approved Quantity ≤ Requested; remarks for reductions or rejections.
  • On completion, Status → Approved.

4.3.5 Pages 50236/50237/50238 – Store Issuance & Posting Pages

  • Approved docs: store enters Quantity to Issue.
  • Post generates Item Journal Lines; updates Issued/Remaining; sets Completely Posted when done.

4.3.6 Page 50251 – Completely Posted Requisition

  • Read‑only archive; filters Completely Posted = true.
  • Highlights Short CLosed using StyleExpr.

4.4 Workflow & State Transitions

  • Open – Requester can create/edit.
  • Approval For HOD – Locked for requester; editable for approver.
  • Approved – Locked for requester & HOD; editable for store.
  • Completely Posted – Read-only archive after full issuance.
  • Short Closed – Early termination; read-only with remarks.

4.5 Business Rules & Validations

Header-Level (Table 50098)

  • No. auto‑generated via No. Series; prevents duplication; traceable.
  • Status default Open; only workflow changes allowed.
  • Location must exist; drives store processing.
  • Dimensions mandatory for audit; budget/report links.
  • Required By Date ≥ Document Date.

Line-Level (Table 50099)

  • Item No. must exist; description/UoM pulled automatically.
  • Required Quantity > 0; respect inventory policy if any.
  • HOD Approved Quantity ≤ Required Quantity.
  • Quantity to Issue ≤ Remaining Required Quantity; set only when Approved.
  • Posting updates Issued Qty.; closes line when Issued = Approved.
  • Short Close requires mandatory remark.

Status Transition Validations

  • Open → Approval For HOD: at least one valid line.
  • Approval For HOD → Approved: each line has HOD Approved Quantity; remarks recorded if reduced/rejected.
  • Approved → Posted: each line has valid Quantity to Issue; inventory availability enforced.
  • Posted → Archived: auto when all issued.

Error Handling

  • “Required Quantity must be greater than zero.”
  • “Approved quantity cannot exceed requested quantity.”
  • “Please provide remarks when short closing a line.”
  • “Item %1 does not exist in the system.”

4.6 Posting & Inventory Movements

4.6.1 Store Role in Posting

  • Open Approved requisition; enter Quantity to Issue, Issue Bin/Location, and remarks if partial.

4.6.2 Business Rules During Posting

  • Check availability at Location/Bin; block if insufficient.
  • Issued Quantity ≤ HOD Approved Quantity.
  • Partial issues allowed; remaining can stay pending or be Short Closed with remarks.
  • After posting: set Completely Posted when all lines fully issued.

4.6.3 Integration with Item Journals

  • Insert Item Journal Lines with Document No., Item, Location/Bin, negative Quantity, Posting Date, Dimensions.
  • Post journal to create Item Ledger Entries (ILE) and Value Entries.

4.6.4 Ledger & Audit Trail

Example ILE:
Item No. = ITM-001
Location = Main Store
Quantity = -10
Source Document = Requisition 5009

4.6.5 Error Scenarios

  • Stock Not Available → block posting.
  • HOD Approved Qty Missing → “Cannot post. Line has no HOD Approved Quantity.”
  • Negative Qty Attempt → “Issued quantity must be greater than zero.”
  • Bin Code Missing (if mandatory) → “Please specify Bin Code before posting.”

4.6.6 Example Posting Flow

Requested: 20 Laptops
HOD Approved: 15
Available: 10
Post 10 now (partial) → ILE -10; Remaining 5 pending
Post remaining 5 later → Completely Posted → archive

4.7 Workflow & User Roles

Roles

  • Requester: Creates/edits during Open; sends for approval.
  • HOD: Approves/rejects with line‑level quantities and remarks.
  • Store: Issues quantities, releases, and posts; manages lots/tracking.

State Machine

Open --Send For Approval--> Approval For HOD --Approve/Reject--> Approved --Release/Post--> Completely Posted

Short Close: Header ShortClosed() requires remarks, removes staged journals, marks Short CLosed.

4.8 Security & Authorization

  • Page access: 50233 requires User Setup."Gen Req HOD Approval"; 50236 requires "Gen Req Store Approval".
  • Field locking: Requester card locks on Approval For HOD; Store card allows Quantity to Issue only.
  • Audit: User IDs and remarks captured at each transition; 50251 archive is read‑only.

4.9 UI/UX Cues & Styling

  • Urgent rows → Unfavorable style; others StrongBold.
  • Short‑closed in archive highlighted with strong accent.
  • Quantity fields use sensible DecimalPlaces and min constraints.

7. TESTING STRATEGY & SAMPLE TEST CASES

7.1 Functional Tests

  • T1 – Create & Send for Approval: Validates status change and field locks.
  • T2 – HOD Approves: Requires HOD Approved Quantity per line.
  • T3 – HOD Rejects: Requires rejection remarks; resets to Open.
  • T4 – Store Issues Partially: Posts partial; updates remaining quantity.
  • T5 – Store Completes Issue: All issued → Completely Posted.
  • T6 – Short Close: Requires remarks; removes staged journals; flags header.
  • T7 – Validation Guards: Blocks invalid issue qty, past required date, or missing approvals.

7.2 Negative/Edge Cases

  • Missing Inventory Setup number series; surface guidance.
  • Item changes after approval; ensure header→line sync.
  • Multiple postings; cleanup Item Journal Lines after post.

7.3 Performance Tests

  • Requisitions with 500+ lines; measure release/post time.
  • Index Warehouse Entry (Location Code, Item No., Bin Code) if needed.

8. PERFORMANCE, RELIABILITY & MAINTAINABILITY

  • Indexes: Clustered on Header No. and Line Document No./Line No.
  • Batch Posting: Release all journals; post once to minimize locks.
  • Error Isolation: Fail‑fast guards before posting.
  • Code Organization: Rules in table triggers + page actions; refactor to codeunits if needed.
